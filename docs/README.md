# 문서 규칙

문서는 번호 순서대로 만든다. 앞 단계 문서가 다음 단계의 기준 문서가 된다.

| 폴더 | 파일 이름 | 내용 |
| --- | --- | --- |
| `0.reference` | `아이디어 정리.md`, `위장형 게임 장르 조사.md`, `생활 시뮬·RPG 메커니즘 조사.md`, `명령어 농장 컨셉 분석.md`, `기술 스택 조사.md` | 만들기 전 조사 |
| `1.architecture` | `wall-geop-lupin 기획·설계서.md` | 전체 기획·설계 (MVP 범위, 마일스톤) |
| | `01_요구사항 정의서.md` | 요구사항 ID (`FR-XXX-01` 형식) |
| | `02_도메인 모델 및 데이터 포맷.md` | 엔터티, 저장 형식 |
| | `03_시스템 설계.md` | 구성 요소, 흐름, 기술 선택 |
| | `04_화면 설계.md` | 화면 목록, 화면별 구성 |
| `2.feature` | `M{n}_{이름} 기능 정의서.md` | 마일스톤 범위(기능 ↔ 요구사항 ID), 규칙 |
| `3.specification` | `M{n}_{이름} 개발 명세.md` | 실제로 만든 내용 (모듈, 명령) |
| `4.issue` | `M{n}_개발 이슈.md` | 만들며 내린 판단, 부딪힌 문제, 남은 확인 항목 |

각 문서 머리에는 작성일과 기준 문서를 적는다.

```markdown
# M1 {이름} 기능 정의서

작성일: YYYY-MM-DD · 기준 문서: `../1.architecture/wall-geop-lupin 기획·설계서.md`
```

개발 이슈 항목은 **현상 → 원인 → 조치 → 반영**(고친 문서·파일) 순서로 적는다.

작업하거나 고친 내용은 크기와 상관없이 같은 작업 안에서 문서에 남긴다. 마일스톤 중의 사용자 요청은 기능 정의서에 날짜를 붙인 K 항목으로 더하고, 개발 명세·개발 이슈·영향 받는 `1.architecture` 문서·루트 `README.md`·`CLAUDE.md`를 함께 고친다 (사용자 요청 2026-11-27).
