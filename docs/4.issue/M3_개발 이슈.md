# M3_개발 이슈

작성일: 2026-11-26 · M3 개발 중 정한 해석과 문제. 항목은 현상 → 원인 → 조치 → 반영 순서로 적는다.

## 1. 한 번에 성장을 계산하면 스프링클러·규칙이 꺼져 있던 동안 일하지 못함

- 현상: M2의 `Engine.Advance`는 구간 전체의 성장을 먼저 계산하고 06:00 이벤트를 나중에 돌렸다. 꺼져 있던 5일을 한 번에 진행하면, 06:00에 스프링클러가 다시 물을 줘도 그 뒤의 성장이 빠지고 규칙도 한 번도 돌지 않는다.
- 조치: 진행을 하루 시작과 규칙 검사 시각에서 구간으로 나눴다. 구간마다 성장 → 경계 이벤트(시세 → 스프링클러 → 계절 → 규칙) 순서다 (정의서 K5).
- 반영: `src/Core/Engine.cs` (`Advance`, `Grow`), 개발 명세 5장

## 2. 스프링클러 칸이 매일 "물 마름"으로 알려짐

- 현상: 스프링클러는 06:00에 물을 주고 다음 06:00까지 유지된다. 구간 끝(06:00)에 물이 끝나므로 경계 이벤트 전에 판정하면 매일 `Dry` 이벤트가 생긴다.
- 조치: 구간 안에서 물이 끝난 칸을 후보로 모아 두고, 경계 이벤트(스프링클러 물 주기) 뒤에도 말라 있을 때만 "물 마름"으로 센다.
- 반영: `src/Core/Engine.cs`, `SprinklerTests.TestDailyWater`

## 3. 한국어 조사가 이름에 따라 어색함

- 현상: `f1에 자동 파종기이(가) 없습니다`, `순무은(는) 제철이 아닙니다`처럼 장비·작물 이름 뒤 조사가 어색했다.
- 원인: 이름이 값으로 들어가서 받침 여부를 문구 표가 알 수 없다.
- 조치: M3에서 새로 쓴 한국어 문구는 조사가 필요 없는 문장으로 바꿨다 (`f1: 자동 파종기 필요`, `순무: 제철 아님`, `이미 있음: 출하함`). M1·M2의 기존 문구(`은(는)` 표기)는 그대로 두었다.
- 반영: `src/Data/Strings.cs` Ko

## 4. 오래 꺼져 있던 뒤의 계산이 느릴 수 있음

- 현상: 최악 조건(Caretaker Lv4 64시간, 배속 5, 검사 주기 10분)이면 게임 1,920일, 검사 27만 번이다. 구역 10개에서 2.2초, 전자동 온실 30개 구역에서 4.2초가 걸렸다.
- 원인: 구간마다 모든 칸을 훑는다 (규칙 조건의 칸 검사, 성장 계산).
- 조치:
  1. 조건 검사는 목록을 만들지 않고 처음 맞는 칸에서 멈춘다 (`Farming.HasRipe`, `HasEmpty`).
  2. 규칙 결과가 바뀔 수 있는 일(새로 다 자람, 하루 시작, 직전 검사에서 농장을 바꾼 규칙)이 없으면 검사를 건너뛰고, 다음에 다 자라는 칸 뒤의 첫 검사 시각으로 바로 간다. 같은 상태면 같은 결과이고, 같은 이유의 실패는 어차피 조용하다.
- 결과: 구역 10개 0.38초, 30개 0.6초. 같은 농장을 12일 한 번에 / 10분씩 1,728번 진행해 골드·창고·씨앗·성장·실행 횟수가 같은지 테스트한다.
- 반영: `src/Core/Engine.cs` (`NextRipe`, `rulesDirty`), `src/Core/Rules.cs` (`Run`이 바뀜 여부를 돌려줌), `RuleRunTests.TestBigStepEqualsSmallSteps`

## 5. 자동 수확기가 있어도 `Ready` 이벤트가 먼저 뜸

- 현상: 실시간에서는 작물이 다 자라는 순간(`Ready` 노란 로그)과 다음 검사(`Auto#1(harvest)`)가 다른 진행에서 일어나, 수확기가 거둘 작물도 매번 `Ready`를 알렸다.
- 조치: 동작 중인 수확 규칙이 그 구역을 맡고 수확기가 있으면 `Ready`를 알리지 않는다.
- 반영: `src/Core/Rules.cs` (`AutoHarvests`), `src/Core/Engine.cs` (`ReportLogs`), `RuleRunTests.TestNoReadyNoiseWithHarvester`

## 6. 슬롯 해석: "켜 둘 수 있는 수" 대신 "위에서부터 동작하는 수"

- 판단: FR-AUTO-06은 켜 둘 수 있는 규칙 수를 슬롯 수로 제한한다. 그대로 하면 컨트롤러를 사기 전에 넣은 규칙이 모두 꺼진 채 들어가서, 산 뒤에 하나씩 `/auto on`을 쳐야 한다.
- 조치: 규칙은 켜진 채로 들어가고, 켜진 규칙 중 위에서부터 슬롯 수만큼만 동작한다. 나머지는 목록에 `wait`(슬롯 대기)로 보인다. 우선순위는 `/auto move`로 정한다 (정의서 K7). 동작하는 수는 슬롯을 넘지 않으므로 요구사항의 의도는 같다.
- 반영: `src/Core/Rules.cs` (`Active`), `../1.architecture/01_요구사항 정의서.md` FR-AUTO-06

## 7. 문구 키 충돌

- 현상: `help.auto`를 `/help` 첫 화면의 한 줄로 쓰려 했는데, `/help auto`의 설명 키(`help.<명령>`, `StringsTests.TestDynamicKeys`)와 같았다. `t.auto`도 인자 없는 제목과 규칙 실행 제목(인자 2개)이 겹쳤다.
- 조치: 첫 화면 줄은 `help.automation`, 실행 제목은 `t.auto_run` `t.auto_run_n`으로 나눴다.
- 반영: `src/Data/Strings.cs`, `src/Core/Commands.cs`, `src/Core/Rules.cs`

## 8. `sell all` 뒤의 개수

- 판단: 02 6.2절 문법은 `sell (crop | all) [number]`이지만 `sell all 10`은 "전부 중 10개"인지 "작물마다 10개"인지 모호하다.
- 조치: `sell all` 뒤에는 개수를 쓰지 않는다 (`rule.err.extra`). 작물별 개수는 `sell <작물> <n>`으로 쓴다 (정의서 K6).
- 반영: `src/Core/Rules.cs`, `../1.architecture/02_도메인 모델 및 데이터 포맷.md` 6.2절
